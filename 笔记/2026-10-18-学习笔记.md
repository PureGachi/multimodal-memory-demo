# 2026-10-18 学习笔记：把本地模型配置放入 .env

## 思路

用户希望把图片描述模型的地址、模型名和密钥放入配置文件，并通过 Git 忽略，减少反复在 PowerShell 设置变量的操作。

模型名不是秘密，密钥才需要保密。采用项目根目录 `.env`；公开的 `.env.example` 继续只展示不含真实密钥的配置格式。

## 结果

- `Settings.from_env()` 使用 `python-dotenv` 读取启动目录下的 `.env`，不向上寻找其他配置。
- 优先级：当前进程环境变量 > `.env` > 默认值。直接传入 `Settings(...)` 的测试仍由调用方完全控制。
- 使用 `dotenv_values()` 返回字典而不修改 `os.environ`，避免旧文件值残留；文件按 UTF-8（兼容 BOM）读取，不进行 `${...}` 变量替换。
- 缺少 `.env` 时保持原有默认行为；可用 `Settings.from_env(env_file=None)` 显式关闭文件读取。
- `.env`、`.env.*` 忽略提交，仅允许两个指定示例文件。检查确认当前 `.env` 未被 Git 跟踪。
- 创建本地单图测试模板，配置 `gpt-4o-mini` 与用户提供的中转地址，`VISION_API_KEY` 留空，未复制聊天中出现过的密钥。
- Settings 的三个密钥字段均不出现在普通 repr 中，但这不代表可以公开序列化整个配置。

参考：[python-dotenv 官方项目](https://github.com/theskumar/python-dotenv)。

## 用户接下来需要做的事

1. 打开根目录 `.env`，只在本机填写新密钥：`VISION_API_KEY=你的新密钥`。
2. 若还没有撤销此前贴进聊天的密钥，先去服务商后台撤销并换新。
3. 使用新的 PowerShell，从项目根目录执行之前的单图测试。不要把密钥或整个配置文件贴进聊天。
4. 修改配置后重跑脚本或重启 API。旧终端中的 `$env:VISION_*` 可能覆盖文件；新终端仍有永久环境变量时，也要检查对应变量。

本地模板是“图片理解 + BM25”测试配置，不是完整参赛配置，不调用 embedding API。读取配置本身不收费；运行真实视觉请求可能收费。此轮没有调用真实付费模型。

## 单图真实测试：HTTP 200 不代表内容可以使用

第一次发送已有设备测试图到用户配置的中转服务，接口返回 HTTP 200，但 `json.loads()` 失败，Add 未提交，也没有进行检索。说明通信返回成功，不代表内容符合项目要求；第一次没有保留模型原始回复，不能断定具体是 Markdown 包裹还是其他非 JSON 内容。

用户进一步提出：需要改代码，在请求中约束返回结构，而不是仅在提示词中要求 JSON。

### 修改内容

- `CompatibleVisionClient` 发送 `response_format`，默认 strict JSON Schema：仅允许 `description`、`visible_text` 两个必填字符串字段，禁止额外字段。
- `CaptionAnalyzer` 继续检查 JSON、字段、类型、每字段 16000 字符上限，以及至少一项含非空证据。Schema 未在请求中设置长度限制，该限制由本地校验执行。
- 不剥离 Markdown、不把任意自然语言冒充结构化结果；拒答与不完整输出也视为失败。
- 非 JSON 诊断只显示字符数与是否 Markdown 代码块，不显示原文。字段错误只显示规则，异常不串联潜在私密输出。
- 新增 `VISION_RESPONSE_FORMAT=json_schema|json_object` 配置。只有显式选择 `json_object` 才使用较弱的 JSON 模式；没有自动降级、自动修复或付费重试。
- 输出模式和 Schema 纳入分析缓存标识，并在 provenance 中记录模式；不能仅依靠可变模型名判断旧缓存仍有效。

参考：[OpenAI Structured Outputs 官方文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat)。第三方服务是否真正遵守参数，仍需实际验证。

### 一次真实验证的结果

修改后仅再发送一次同一张图片，关闭本地 OCR 和 embedding，只使用远程图片分析 + BM25。HTTP 200，Add 成功，搜索 `M42冷却水泵` 返回 1 条原图记忆。

模型输出 `visible_text`：

```text
设备型号：M42
设备名称：冷却水泵
维护提示：每周检查水位
```

人工查看原图，三行文字一致；description 是英文的设备资料布局概述，没有声称图中实际拍到一台水泵。

报告：`data/evaluations/images/20261018T131127Z-a586b84a.json`，原图副本同目录同文件名前缀 `.png`。工作台刷新报告列表后可查看。此报告不包含 API 密钥。

这只证明该服务本次接受图片和结构化参数并返回了合规结果，不能证明平台内部模型身份、正式参赛合规性或复杂照片准确率。单图检索没有干扰项，不构成召回率评估。

最终回归 **133 passed**。新增测试涵盖请求 Schema、显式 JSON 模式、缓存版本差异、服务商忽略 Schema 的异常输出、拒答、错误配置、HTTP 400 不降级及隐私保护。

## 继续接通 embedding：DashScope 示例与项目适配的关系

用户提供阿里云示例 `dashscope.TextEmbedding.call(model="text-embedding-v4", input=...)`，希望继续修改 embedding 工具。核心是模型名与输入文字；调用 SDK 的方式不等于模型本身。本项目已有阿里云 OpenAI 兼容 HTTP 适配器，因此不再安装第二套 DashScope SDK。原生 API 和兼容 API 的地址与响应结构不同，不能混用。

本次完善：

- 保留本地 Ollama、离线 BM25 和远程 text-embedding-v4 三种模式，不自动启用远程调用。
- 在本地 `.env` 新增独立 `EMBEDDING_*` 配置占位，密钥留空，未复用视觉密钥。用户需要把 `MEMORY_EMBEDDINGS=none` 改为 `compatible` 后才启用。
- 适配器拒绝误填完整 `/embeddings`、`/chat/completions` 路径，避免重复拼接。HTTP 错误仅显示状态与白名单错误代码，隐藏上游正文与异常链。
- 新增 `evaluation/embedding_probe.py` 与 `scripts/embedding_smoke.py`，实际走 Add/Search、临时数据库、3 条文字干扰项 + 1 个问题；正常 2 次 embedding 请求，不调用视觉 API。
- 输出纯向量排序与实际融合结果，检查返回维度和不同用户隔离。Search 的 BM25 降级不会被当成向量成功。
- `--check-only` 不调用网络、不写报告，只输出模式、模型、维度以及地址和密钥是否已配置。真实调用需 `--allow-remote`，报告保存到 `data/evaluations/embeddings/`，暂不进入工作台报告列表。
- 工作台可选择远程 embedding，前后端都要求明确勾选费用确认；提示整场景全部历史都会被向量化。图片按钮显式固定本地 OCR，不意外继承已配置的付费视觉 API。

本次配置预检：模型 text-embedding-v4、1024 维，地址和密钥均未配置，当前模式仍为 none，**没有发出真实 embedding 请求**。因此不能宣称已经成功连接阿里云。

回归测试增加真实受控 Add/Search 小测试、查询向量故障拒绝假成功、返回 index 重排验证、误填 endpoint 拒绝、错误隐私保护与工作台付费确认。最终 **140 passed**。

## 完整数据集测试失败后：错误模块与断点续跑

### 思路

用户要求继续使用已有 Mem-Gallery 测完整对话。AI/机器人场景共 12 个会话、185 轮、370 条消息、31 张图片、57 个问题，原图齐全。尝试使用远程视觉 + text-embedding-v4 后，在 Add 的向量阶段失败，未生成完整报告。旧的临时目录设计不能保留已完成工作，通用错误也无法区分网络与向量格式。

用户提出建立 error 小模块、统一错误反馈，并补上保存进度与续跑。这是软件工程层面的可靠性改进，不是更换检索算法。

### 结果一：类型与反馈分离

- `memory/errors.py` 继续定义业务异常；`ModelUnavailable` 新增错误代码、组件、HTTP 状态、服务商代码和可恢复标记，保留旧调用方式。
- 新增 `memory_app/errors.py`，用静态错误目录生成中文说明和建议，不序列化异常原文或 cause，也不打印 provider 请求/响应正文。
- embedding HTTP 适配器区分 timeout、network_error、http_error、invalid_response；视觉 SDK 适配器对应区分超时、网络、HTTP、响应问题。图片解析区分 invalid_json、invalid_schema 和 refusal。
- HTTP API、三个 CLI、检查点状态共用安全反馈。API 的业务错误仍是 detail 字符串，并增加结构化 error；不会更改成功 Add/Search 的格式。
- retryable 只是人工排查参考，没有自动增加重试、降级模型或付费请求。

参考：[OpenAI SDK 错误处理](https://developers.openai.com/api/reference/python/)。

### 结果二：任务级持久化与两层缓存

新增 `evaluation/checkpoint.py`：每个评测任务有独立持久目录，包含 state.json、记忆数据库、模型结果/逐题结果数据库和媒体文件。新建任务默认启用，老的 `evaluate()` 单元测试调用仍可用临时目录。

1. Add 成功的历史轮次保留在数据库，重放相同请求直接使用已有记录。
2. 图片分析通过校验后就保存到任务模型缓存；即使之后 embedding 失败，分析也能复用。
3. embedding 按文本哈希、query/document 角色、模型版本缓存；每个成功批次保存，失败批次不假装成功。
4. 逐题结果成功后保存，恢复时跳过已完成问题。
5. 原始数据哈希、图片内容、选中问题、K、模型版本、视觉协议等组成指纹；不匹配则在付费计算前拒绝续跑。
6. 用 OS 文件锁排除同一检查点的并发使用；状态 JSON 原子替换，避免半写入。进程强制退出时锁释放，但最后记录的 running 状态可能保留。
7. 修复恢复时的来源映射：根据 Add 的确定性 ID 还原轮次，不能把数据库中已有的所有消息错误归给第一轮。

这些失败模型结果的额外缓存仅属于隔离的评测任务；生产 Add 原有的原子提交语义不变。

### 用户怎么查看与续跑

启动新版评测会先打印 Checkpoint 目录。失败时 state.json 记录阶段、轮次/题号、完成数和结构化错误。保留相同命令参数，追加 `--resume '实际检查点目录'` 即可手动续跑，不需要重新建库。

工作台增加“进度、错误与断点”区域和只读 `/api/checkpoints`，可刷新查看状态。当前恢复入口是 CLI，没有自动重跑按钮；“开始评测”仍是新建任务，不能代替续跑。报告只在所有问题完成后生成，失败不显示为零分。

### 不能保证什么

- 此前旧版失败运行没有检查点，临时进度无法事后恢复。没有假称已找回，也没有再次调用付费数据集。
- 已保存的成功结果可复用，但“服务商处理成功、响应丢失或本地尚未保存”存在窗口，不能保证零重复计费。
- 缓存和检查点包含数据/派生结果，也需要隐私保护和按期清理，不可提交 Git 或公开下载。
- 本次测试没有确定之前那次真实故障究竟是网络还是响应格式；只能保证今后的错误会细分。
