01 / Start here

从一条记忆出发，
理解整个项目。

这个系统做两件事：把历史消息和图片保存好；当你提出问题时，找回可能有帮助的原始消息和原图。V0.2 在这个基础上，增加了可配置的图片描述与 OCR 链路。

说明文档日期：2026-10-11 · 对应代码版本：0.2.0 · 面向正在学习 Python / FastAPI 的开发者

补充更新 2026-10-13：本地 OCR 已安装，并通过三张清晰文字图的真实识别与检索检查。详见第 07 章更新说明；复杂照片质量和远程视觉仍待验证。

先记住这一句：main 负责把工具准备好，MemoryService 是业务入口，Add / Search 负责安排步骤，各个功能模块负责完成某一件具体的事。

我们到底想解决什么问题？

假设你曾上传一张设备照片。照片里的铭牌写着 M42，但你发消息时只写了“这是今天拍的设备”。几天后你问：“之前那个 M42 的设备照片在哪里？”如果系统只检索你输入的文字，历史里并没有 M42，可能就找不到。

V0.2 的方案是：在写入时分析图片，得到“设备面板、红色指示灯”等描述，以及“型号 M42”等可见文字。把这些派生文字加入检索，但依然保留原始消息与照片。搜索命中派生信息后，再沿着 ID 关系找回原始证据。

上面的图，像“先存资料，再翻资料”

从左往右读。箭头表示资料经历了哪些阶段，不是说上传一次图片就会立刻执行搜索。

  1. 历史图文：你上传设备照片，附带一句“今天拍的”。这是输入。
  2. Add：系统检查输入，必要时读图、提取文字，并准备以后查找所需的索引。
  3. 持久化：把资料真正保存下来，程序关闭后还在。不是只放进临时变量。
  4. Search：过几天你问“M42 的照片在哪里”，系统才执行查找。
  5. 原始证据：返回之前那条消息和照片，而不是重新画一张图或编一段回答。

这张图只要记住：Add 是整理入库，Search 是按问题找回；中间的存储把两个时间点连接起来。

02 / System architecture

谁安排流程，谁完成工作？

按功能分模块的目的，不是让目录看起来专业，而是让你修改某一种能力时，能够预料哪些地方会受到影响。

上面的架构图，按“谁把事情交给谁”来读

从上往下读。每个框不是一台独立服务器，而是我们程序里的职责层。向下的箭头大致表示调用：上层把工作交给下一层，结果再沿调用关系返回。

  1. 外部调用者：可以是你运行的脚本，它向 /search 发请求。
  2. API：像收件窗口，核对请求格式与访问凭据。它不在这里计算相似度。
  3. MemoryService：像业务柜台，提供统一的 add()、search() 方法。外部不必逐个调用所有工具。
  4. Add / Search：像办事步骤单，决定先做什么、后做什么、失败怎么办。
  5. 底部三组能力：是真正干具体工作的工具。“内容能力”读图或生成向量，“检索能力”找候选和排序，“持久化能力”存数据库与文件。

底部左右分组不是先后顺序。不是“先做完内容模块，再必然做检索模块，再做存储模块”；Add 和 Search 会按各自需求选用这些工具。

main 没画在主链里，是因为：它开机时把工具准备好，之后每次请求不用回到 main 重新安排一遍。

main 不是“每件事都要经过它”的总管

它更像开店前的准备工作：读取配置、创建数据库对象、准备媒体目录、创建模型适配器、建立 MemoryService，再把路由接到服务上。店开起来之后，客户的每个查询由路由交给 service，service 再交给 Search 流程。无需返回 main 重新安排。

如果把搜索细节全写在 main 中，入口会同时知道 HTTP、模型调用、排序、图片恢复与数据库细节。以后修改检索时，会碰到启动代码；写单独的检索测试也更困难。现在 main 仍然知道具体实现——因为总得有一个地方负责“选哪一种工具”——但不负责每次操作的步骤。

为什么 MemoryService 和 add.py / search.py 都存在？

MemoryService 持有准备好的工具，向外提供稳定的两个方法，统一记录耗时并处理文件系统错误。add_memory() 与 search_memory() 则是独立流程函数，安排具体步骤。你可以把前者看成“柜台”，后者看成“办理存入／查找业务的工作流程”。

模块知道什么不应该承担什么例子
API 知道请求格式不实现向量排序top_k 是否在 0–100
Add 知道写入顺序不直接拼视觉 HTTP 请求分析完成后才保存与提交
vision 知道分析任务不决定整个 Add 是否提交要求输出两个字符串字段
llms 知道服务协议不写入记忆数据库发送 Base64 image_url
storage 知道怎样存数据不负责理解图片把原始记录与向量同事务提交

这是不是复杂的“插件架构”？

不是。当前没有插件注册中心，也没有让所有模块继承同一个大基类。embedding 和图片分析分别声明了 Protocol 能力约定，其余工具主要按方法名称协作。代码通过参数传递对象，仍然是一套容易追踪的小型实现。

04 / Composition

服务还没接到请求时，
已经准备了什么？

“启动”与“执行一次查询”是两个时间段。先分清它们，main.py 就容易理解了。

启动命令进入哪里？

.\.conda\python.exe -m uvicorn memory_app.main:create_app --factory --host 127.0.0.1 --port 8000

memory_app.main:create_app 指向 main.py 中的工厂函数。--factory 告诉服务器调用这个函数取得 FastAPI 应用。不是每来一个请求就重新创建整个应用。

1 · 读取 Settings

如果调用者没有传入 settings，就调用 Settings.from_env() 从环境变量读取。比如数据目录、Ollama 地址、是否启用图片分析。配置只描述“我们想使用什么”，它本身不会读图或生成向量。

2 · 创建分析器与存储对象

build_vision(settings) 根据开关创建视觉 API 分析器、OCR，或组合 pipeline；都关闭则为 None。随后创建 SQLiteStore、LocalMediaStore。数据库初始化可能迁移旧向量表。配置错误先报错，避免无效配置却先打开并迁移数据库。

3 · 准备文本 embedding

启用 Ollama 时，创建 OllamaEmbedder。它会检查模型列表并记录模型 digest，作为向量版本的一部分。即使图片分析关闭，文本向量仍可以独立启用；反过来也可以只用 OCR + BM25。

4 · 把工具交给 MemoryService

创建服务对象，再把这个对象交给 API 路由。之后路由不必知道数据库文件在哪里，只需要知道 service 有 add 与 search 方法。

# 对照 main.py 的关键装配语句
service = MemoryService(
    store, media, embedder, SQLiteVectorStore(store), vision
)
app.include_router(build_router(service, settings.api_key, settings.embeddings))

这就是“依赖注入”吗？

是的，这里使用的是很朴素的构造函数／参数传递。依赖是流程需要使用的工具；注入是由外部创建好工具，再通过参数交给流程。不是黑客输入，也不需要特殊框架。

# 流程没有自己写死“连接某个模型”
def add_memory(payload, store, media, embedder, vectors, vision=None):
    ...  # 使用传入的工具

# 测试时，可以传入输出可控的 embedder / vision
app = create_app(settings, embedder=test_embedder, vision=test_analyzer)

这样测试数据库故障时，不需要真的调用付费视觉模型；测试向量失败时，也不需要故意关掉你正在用的 Ollama。我们替换的是工具对象，而不是重写整条 Add 流程。

Protocol 又是什么？

它描述对象应当提供哪些成员。例如 ImageAnalyzer 需要 version 和 analyze(raw, mime)，返回 ImageAnalysis。它类似接口说明书，帮助阅读和静态检查；不是必须继承的插件基类，也不会自动确保远程服务输出正确。输出格式检查依然要在适配器里完成。

05 / API boundary

外部数据，怎样进入流程？

API 是外界和内部代码约定的入口。HTTP 是传递请求的方式，JSON 是请求的表示格式，payload 是“这次携带的数据”的通用叫法。

一次 Add 的示例

{
  "request_id": "photo-001",
  "user_id": "alice",
  "session_id": "session-1",
  "messages": [
    {
      "role": "user",
      "content": [
        {"type": "text", "text": "这是今天拍的设备"},
        {"type": "image_url", "image_url": {
          "url": "data:image/png;base64,这里是实际图片的Base64数据"
        }}
      ]
    }
  ]
}

这是结构示例，不是可直接提交的图片数据。当前接口接受内联 PNG / JPEG / WebP Data URI，不会自动下载任意网络图片链接。普通纯文字消息的 content 也可以直接是字符串。

字段实际含义不能混淆的地方
user_id这份记忆属于谁是数据隔离范围，不等于 session_id
session_id这条消息来自哪次会话当前 Search 不要求指定它，也不会只搜一个会话
request_id标识这一次 Add 请求重试同请求应保持相同 ID 和内容
messages一批用户／助手消息每条消息是一个 Unit，不是整批一个 Unit
timestamp可选的原消息整数时间戳保留但当前不用于时间截止过滤

先弄懂 schema：它是一张“填写规则表”

你可以把请求当成一张表单：user_id 填谁的资料，query 填想找什么，top_k 填最多要几条。schema 规定表单有哪些格子，每格允许填什么，哪些不能空。它不负责真正搜索，就像表单的填写要求不会替你办理业务。

你记得的 AI 工具接口也是这个意思。工具的“用途描述”告诉 AI 什么时候使用它；参数 schema 告诉 AI 调用时怎样填参数。注释或自然语言描述可以帮助理解，但描述本身不等于完整的 schema。

用两个 top_k 例子读这张图

填 5：满足整数和 0–100 范围，能通过这一项格式检查。其他字段也合法、鉴权通过后，才进入 Search，最后最多返回 5 条消息。

填 -1：数据到 schema 这一步就被拦下，返回 422。不会先搜索再删掉结果。

填 5 但问题根本没有证据：格式仍然合法。schema 不知道历史资料能否回答问题，那是检索效果与后续判断的事情。

schema 问“你有没有按规定填写”，Search 问“资料里能找到什么”。

# api/schemas.py 中的实际定义
class SearchRequest(BaseModel):
    query: Content
    user_id: Identifier
    top_k: Annotated[StrictInt, Field(ge=0, le=100)]
    options: list[str] | None = None
代码怎么写翻译成人话你先关注什么
class SearchRequest(BaseModel)定义一份搜索请求的数据规则，交给 Pydantic 检查这是格式声明，不是搜索算法
query: Contentquery 必填，可以是规定的文字或图文内容冒号后面写的是允许的数据类型
user_id: Identifieruser_id 必填，而且不能只有空白它标记本次查谁的记忆
StrictInt、ge=0、le=100严格整数，大于等于 0、小于等于 100不是任意字符串或负数都能填
options ... = Noneoptions 可以不提供；默认没有额外提示等号后的值是默认值

读这张表时：先看第二列，把规则读成一句普通话；再回到第一列找对应写法。不用第一次就记住 Annotated 的全部语法。建议打开 src/memory_app/api/schemas.py，先读 SearchRequest，再读 AddRequest，最后才往上追 Content、Identifier 是怎样定义的。

路由里发生了什么？

@router.post("/add", dependencies=[Depends(authorize)])
def add(body: AddRequest):
    return service.add(body.model_dump(mode="json"))

FastAPI / Pydantic 先根据 schemas.py 检查字段和类型；鉴权函数检查配置的 API Key；model_dump() 把请求模型转换成普通字典。这个字典交给 service，到了 add_memory 中就叫 payload。

注意有两层验证：schemas 检查“结构像不像一条合法请求”；parser 和图片验证继续检查“文字是否只有空格、图片字节是否合法、MIME 是否真实、大小是否超限”。有 image_url 字段，不代表里面就真的是图片。

Search 的格式更简单

{
  "user_id": "alice",
  "query": "之前型号 M42 的设备照片",
  "top_k": 5,
  "options": null
}

query 可以是文字，也可以是图文块。top_k 是最多返回多少条消息，不是几张图片或几个片段。options 是可选的文字提示，会拼进查询文字，不是已经确定的答案，不会写入记忆。top_k=0 返回空列表；允许范围是 0–100。

HTTP 状态码在告诉你什么？

200 是操作成功；401 是鉴权失败；409 是同 request_id 的内容冲突；422 是请求内容不合法；503 是模型或存储不可用。不要遇到 503 就换一个 request_id 盲目重发；修复问题后，用原请求重试通常更合适。

上面的 Add 图，是“存一条记忆”的步骤单

从上到下逐框读，每一行的 → 表示框内的小调用顺序。例如“enrich_images → analyze_cached → vision.analyze”表示：先安排这张图的分析，检查是否能复用，只有缓存没命中时才真的调用模型，不是每次都必走三个函数。

  1. 接请求：API 把已经过格式检查的数据交给服务，服务进入 Add。
  2. 查重试：先问“这次请求之前是不是已经成功了”。成功重放可走快捷返回，不再执行下面所有步骤。
  3. 解析：把消息整理成 Unit，把图片解码，并记下原始顺序。
  4. 图片分析：开关打开时才做。比如原图提取到“红色灯”和“M42”；不开启就跳过。
  5. 建立向量：原话、图片描述和可见文字分别成为检索线索，并保留所属消息。
  6. 落盘与提交：原图写进媒体目录，消息与索引写进数据库，成功后才告诉调用者完成。

这张图最重要的不是背函数名，而是：先验证和计算，再保存与提交；Add 统筹，模型与存储各做自己的工作。

第一步：先确认这是不是重试

Add 对整个请求生成 payload_hash，再查看 requests 表里同用户、同 request_id 的记录。如果哈希相同，说明这次是已成功请求的重放，不需要重新算向量或再次分析图片。如果哈希不同，则返回 409，防止一个请求 ID 指向两份不同内容。

重放分支仍会从原请求解析图片并执行 media.put。原因是数据库记录可能还在，但原图被误删了；相同请求重试可以补回原图。这不是给历史图片补描述：模型开关变化后，重放仍不会重做分析。

第二步：解析整批消息

假设消息有“文字、图片、文字”三个块。parser 返回四份东西：可存储的有序 content、拼接后的原始文字 text、图片 keys、解码后的图片字节。content 里的图片不继续保存很长的 Base64，而是保存 media_key 和 MIME；以后读取时恢复 Data URI。

每条消息生成一个 Unit。它的 ID 由用户、请求 ID、消息序号确定，所以同一次重试得到同样身份。流程先验证整批消息，再启动图片模型；否则前面的图片已经收费，最后一条非法消息又使整批失败，就会产生不必要的费用。

第三步：给图片增加派生资料

如果 vision 为 None，跳过。否则 images.py 遍历每条消息里的图片，从当前请求缓存或数据库缓存复用分析；没有缓存才调用分析器。比如得到：

{
  "description": "设备面板上可见一盏红色指示灯",
  "visible_text": "型号 M42"
}

这些文字被放进 Unit.image_artifacts，不覆盖 Unit.text，也不改写用户的 content。每张图在一条消息中对应一个 artifact；同图在不同消息出现时，分析文字可以复用，但 artifact 仍各自关联到不同消息。

第四步：把不同来源分别建立向量

indexing.py 枚举原文、图片描述、可见文字，每种来源分别按 400 字符分片。每个片段记录所属 unit_id、source、块序号。embedding 模型返回向量后，再把这些来源信息与向量配对。这样即使三种来源都从第 0 块开始，也不会互相覆盖。

第五步：保存与提交

模型工作全部成功后，media.put 保存原图。接着 storage.commit_add 开启短写事务，再检查一次幂等状态，写入 Units、图片分析缓存、向量和 requests。第二次幂等检查是为了应对多个请求并发：它们可能都在一开始查到“还没写”，但真正提交时只能有一份成功记录。

这不是跨文件系统和数据库的分布式事务。图片保存后，数据库如果提交失败，可能留下未引用文件；但消息和向量不会一半成功一半失败地被 Search 看见。未引用文件的自动清理仍未实现。

先区分四种能力

能力输入 → 输出V0.2 状态
原图存储图片字节 → 本地文件已实现，不理解内容
图片描述图片 → 可见场景文字可配置远程分析器，真实效果待验证

直接图片 embedding图片 → 视觉向量未实现，不要和描述的文本向量混淆

vision/caption.py：规定“让模型做什么”

CaptionAnalyzer 准备提示词，要求描述看得见的物体、颜色与关系，转录能读清的文字，不猜测隐藏原因，不服从图片里的指令。结果必须是仅含 description、visible_text 两个字符串的 JSON 对象，每个字段最长 16000 字符；两者都为空则视为无效 caption。

它不接受代码块包裹的 JSON，也不会偷偷把格式错误解释成“没有信息”。严格格式会让一些服务输出失败，但避免无效分析被当成成功入库。提示词只是减少幻觉与图片提示注入风险，不保证模型一定遵守。

llms/compatible.py：规定“怎样向服务发送”

CompatibleVisionClient 把图片编码为 Data URI，按 Chat Completions 的 image_url 格式发送到配置的 HTTPS 地址。一次请求一张图，设置输出 token 上限与超时，要求 finish_reason 为 stop，再取 message.content。它负责 HTTP 错误和响应结构，不负责保存结果。

“兼容”不等于任何自称兼容的服务都能直接用。有些模型不支持图片，有些输出格式不同，有些推理参数需要额外配置；必须用实际账号做一次验证。当前不会自动重试远程调用，避免不透明地重复付费。

vision/ocr.py：本地专门读文字

TesseractAnalyzer 使用已安装的 Tesseract 命令。初始化时读取引擎版本；分析时把图片转为 RGB PNG，放进临时目录，然后启动带语言参数的进程，读取 stdout 文本。命令参数以列表传入，没有 shell 拼接。无文字图片识别为空是合法结果。

OCR 不能代替场景理解：一个没有文字的红色按钮，可能被 OCR 输出为空；这不是“图片没存好”。中文识别需要对应语言包。当前不是自动下载 OCR 模型，也没有承诺小字、模糊图或复杂版面一定准确。

pipeline：可以任选，也可以组合

上面的三个框，是三种配置选择，不是三个必经步骤

横着读，比较每个框能提供什么。例如一张铭牌照片：远程视觉可以描述“这是一块设备铭牌”，也可以转录文字；只用 OCR 时主要读“M42”等字符，不知道画面是什么物体；两者组合时依次调用，再拼接文字。

再换成一张没有文字的红色按钮照片：OCR 很可能合法地返回空文字；远程视觉则有机会描述按钮与颜色。所以“只启用 OCR”不等于拥有全部图片理解能力。

第一版可以只选一种。组合不是自动更准确，也不是两个模型互相纠错；它可能增加线索，也可能增加重复和误读。

ImagePipeline 将分析器输出合并。任意启用的分析器失败，整次图片分析失败；不是“其中一个失败就自动忽略”。缓存版本由各分析器版本组合而成，能够区分模型、提示词、语言或手动 revision 的变化。

为什么还要记录 providers？

为了以后发现错误时能知道是谁生成的。artifact 保存模型名、服务地址、提示词哈希或 OCR 引擎与语言、revision 等来源，不保存 API Key。组合后的 visible_text 是拼接文字，当前没有细粒度坐标、置信度或每个字符的独立来源。

08 / Data model

搜到一个向量以后，
怎样找回那张图？

关键不是“向量里藏着图片”，而是每份派生数据都留下了来源 ID。向量查找解决相似性，ID 关系解决追溯。

上面的关联图，是“按编号找回来源”，不是运行步骤

从最上面的向量往下追。可以把向量看成帮助查找的线索卡，unit_id 是卡上写着的消息编号；artifact_id 标记哪份图片分析结果，media_key 标记哪张原图。

  1. 搜索找到了一个相关向量，它的 unit_id 是 U1。
  2. 通过 U1 找到原始消息；假设它写着“今天拍的设备”，并带有一张图。
  3. U1 的 image_artifacts 里，有分析记录 A1，里面写着“M42”，并记录对应的 media_key。
  4. 把媒体根目录 root 和 media_key 拼起来，就能读取原图文件。

不要误读为“图片先变成向量，再从向量还原图片”。向量不包含可逆的完整图片。我们靠编号关系去读早已保存的原图。

实际返回时可以更直接：向量 → Unit → Unit.content 里的 media_key → 原图；artifact 的作用是保留分析线索和来源，不要求每次取图都先遍历它。

Unit 是什么粒度？

一个 Unit 对应一条用户或助手消息。它可以是纯文字，也可以包含几段文字和几张图片。一轮 user + assistant 对话通常是两个 Unit；一条长消息分成多个向量片段后，仍只有一个 Unit。最终 Search 的 top_k 也是按 Unit 计。

Unit 字段保存内容用途
id / user_id / session_id消息身份、所属用户、来源会话关联、隔离与追溯
role / timestamp / created_at角色、原消息时间、写入时间保留上下文；当前不做时间过滤
content字符串或有序内容块，图片用 key 引用恢复用户提供的原始证据
text用户原始文字块拼接原文检索来源，不混入生成描述
media_keys这条消息引用哪些图片图片哈希匹配、预算与读取
image_artifacts图片派生结果列表扩充检索，记录模型来源

SQLite 里并不是“一切都在一张表”

units 保存消息 JSON（其中嵌入 artifacts）；vectors 保存向量与来源字段；requests 保存已成功请求的哈希；image_analyses 是分析结果缓存，按用户、media_key、分析版本复用 description 与 visible_text。缓存不代替每条消息自己的 artifact 记录。

# 同一消息可以有这些向量来源；各自块序号从 0 开始
unit_id="U1", source="text",                       chunk_order=0
unit_id="U1", source="image:A1:description",       chunk_order=0
unit_id="U1", source="image:A1:visible_text",      chunk_order=0
unit_id="U1", source="image:A2:description",       chunk_order=0

media.key、root、put 到底是什么关系？

# 启动时：给媒体对象指定根目录
media = LocalMediaStore(settings.data_dir / "media")

# 解析图片时：根据用户与原始字节生成相对标识
key = media.key(user_id, raw)

# 写入时：真正拼出磁盘位置
target = self.root / key
# 然后 put 将 raw 写到 target

root 默认是 data/media；key 形如“用户 ID 的 SHA-256 / 图片字节的 SHA-256”。拼起来就是最终文件路径。raw 是二进制字节，不是 Base64 字符串；MIME 记录图片格式。文件名没有 .png 后缀，也不妨碍里面保存真实 PNG 字节。

哈希不是加密，也不是图片向量。同样字节得到同样 key；裁剪、重新压缩后，即使肉眼像同一张图，也可能得到另一个 key。图片哈希匹配不能代替语义相似图片检索。

恢复原图在哪发生？

evidence.compose 读取候选 Unit，按原始 content 顺序保留文字，再通过 media.uri(key, mime) 读文件并生成 Data URI。模型描述不自动加进返回 content，所以外部看到的仍是原始消息，而不是系统生成的替代文本。

系统怎样找？

Search 不是拿问题去和所有原图直接比较。当前主要把问题变成文字检索和文本向量检索，再把候选消息融合。

上面的 Search 图，是“几种找法分别找，再合成一份结果”

先读顶部，再读中间三个并排框，最后读底部。并排表示三条候选路线，不表示同时开了三个线程；当前代码按顺序组织这些调用。

  1. 准备问题：你问“M42 的照片在哪里”，先取出查询文字，并限定只读你的记忆。
  2. BM25：找哪些历史原文或图片提取文字含有 M42 等词，比较文字线索。
  3. Dense：把问题转成向量，找意思接近的历史片段，不要求用词完全相同。
  4. 图片哈希：只有你用图片来查时才适用，找字节完全相同的图。纯文字问题不会凭空走这条路线。
  5. RRF：收集各路消息名次，合并成一个消息排行榜。不是再调用一个大模型判卷。
  6. 恢复证据：根据消息编号读原始内容和图片，返回给调用者。

中间的三路产物是“候选消息排名”，底部才是最终返回的原始资料。候选不一定有用，也不保证有完整答案。

1 · 先确定查询范围和文字

parser 解出 query 的文字和图片 keys。options 中的文字拼进查询。读取 user_id 下所有 Units；top_k=0 或该用户没有记录时立即返回空，不调用图片模型。当前是用户级全历史搜索，不根据会话或提问时间截断。

2 · 如果问题是一张图片

启用分析器时，临时分析查询图片，或者复用同用户已有的 Add 分析缓存。得到的描述与可见文字加入这次查询，不写入 Units、不保存查询原图、不将新结果写入持久缓存。已有哈希匹配仍然保留。

如果图片模型失败，保留输入中的文字和哈希路线继续查。这种降级不等于模型已经成功理解图片；对一张从未见过、没有文字的查询图片，降级可能找不到任何内容。

3 · BM25 搜索的是“扩展检索文字”

retrieval_text 把原文、description 和 visible_text 合在一起，生成只用于本次检索的 Unit 副本。原 Unit.text 不被改写。所以用户原话没有 M42，但图片 OCR 中有 M42，仍有机会通过关键词命中。

4 · Dense 搜索的是独立来源片段

对查询文字分片并生成查询向量，再查询同用户、同 embedding 版本的向量。每条消息可能有很多原文／描述／OCR 片段；当前取其中最高相似度作为该消息的 Dense 分数，不是把所有片段先平均。

5 · 合并，再恢复证据

每路候选深度为 max(top_k * 3, 30)。候选深度不是最后返回条数：多取一些供融合，再返回最多 top_k 条消息。RRF 汇总 unit_id 后，compose 恢复完整原文和图片。多个片段命中同消息，不会重复占据多个结果位置。

“返回了东西”不等于“确实有答案”。向量路线当前没有可靠的相关性阈值，无证据问题也可能返回候选。缺少某条结果还可能是图片预算导致 compose 跳过该消息，不一定是排序里没有它。

  "data": [

这是简化结构示例。score 是融合后的排序分，不是回答正确概率。created_at 是写入时间，不是照片拍摄时间。接口当前不输出最终自然语言答案，也不自动说明哪些 OCR 字符支持这次命中。

10 / Retrieval mechanics

理解四个步骤，
就能看懂当前混合检索。

分片决定每个向量代表多大范围；embedding 生成表示；检索给候选排序；RRF 再组合排名。这几件事应分别调试，不要混成一个“模型好不好”。

一 · 分片：长文字为什么不只做一个向量？

一条很长的消息可能讨论旅行、设备、价格等多个主题。只做一个整体向量，某个小细节可能不够突出。因此我们把每个来源文字按 400 个 Python 字符切开，片段分别建向量。当前没有重叠、不按句子边界、不按 token 数切分；中文、英文字符都计入长度。

原文来源 text：          950 字符 → 第0块400 + 第1块400 + 第2块150
第一张图 description：  120 字符 → 独立第0块
第一张图 visible_text：  30 字符 → 独立第0块
搜索命中任何一块 → unit_id → 返回完整原消息

短查询和长历史确实有信息稀释风险；分片只是缓解，不保证解决。句子被切断、必要上下文分散到两块也可能影响效果。是否加重叠或按句子切，要用失败案例和对照实验判断。

二 · embedding：把文字映射为数值表示

OllamaEmbedder 使用配置的模型。此前本机 nomic 输出为 768 维；维数来自模型，不是流程里写死“768 个关键词”。向量的每一维通常不能直接解释为“红色”“设备”等词。

入库文字加 search_document: 前缀，查询加 search_query: 。每批最多 16 段，禁止服务静默截断。返回结果要检查数量、数值、有限性、非零范数与批次维数一致，再做 L2 归一化。版本包含模型 digest、前缀版本与 chunk400，避免把不兼容表示混在一起。

归一化之后，代码用点积比较两个向量，相当于比较余弦相似度。对某条消息的多个片段，取最高匹配分。查找仍遍历该用户同版本的全部向量，所以这里不是 HNSW 等近似索引。

三 · BM25：保留精确文字线索

词法路线将英文小写化，按字母／数字／下划线分词；中文加入单字和相邻双字。没有中文分词模型、停用词表或查询改写。BM25 考虑词是否出现、出现频率、在多少文档中常见及文档长度，帮助型号、专有名词等精确词命中。

当前 BM25 的一份“文档”是一个 Unit 的原文加派生文字，不是每个 400 字符片段。不要把 embedding 的分片规则误认为 BM25 也按相同块建立索引。

四 · RRF：看名次，不直接比较分数

BM25 分数和向量相似度不在同一个刻度上。RRF 不直接相加它们，而是给每路中排第 r 的候选一个贡献：

贡献 = 1 / (60 + r)
同一消息的最终分 = 它在各条路线中的贡献之和
消息BM25 名次Dense 名次RRF 总贡献（约）
A131/61 + 1/63 ≈ 0.03227
B211/62 + 1/61 ≈ 0.03252
C未进入候选20 + 1/62 ≈ 0.01613

上面的 RRF 表，先一行一行横着看：A 在 BM25 排第 1，就得到 1/61；在 Dense 排第 3，再得到 1/63，最后相加。C 只进入 Dense 候选，所以只有那一路贡献。“未进入候选”不是减分，只是没有这一份加分。再竖着比较最后一列，数字越大排得越前。

这个例子里 B 综合后排在 A 前面，即使 BM25 的第一名是 A。融合并不保证胜过最强单路；一些有用候选也可能被混合排名挤出前 K，需要实际检查。

HNSW 是哪里的一种替代方案？

它替代的是“怎样在很多向量中找近邻”的部分，不替代图片理解、embedding 或 RRF。当前线性扫描简单、容易核查，数据增大后才需要根据延迟与容量考虑更高效的索引。换索引也不能弥补图片描述没有提到目标细节。

怎么定位一次漏检？

先看原文／派生描述里是否有目标信息，再看 BM25 与 Dense 单路是否找到，最后看融合是否挤掉结果。只有弄清漏在哪一层，调整才有方向。

11 / Reliability

正确的架构，也要明确
“失败时会发生什么”。

Demo 不只是正常路径的几次函数调用。重试、半成品、跨用户混淆和重复计费，都需要能说清楚。

Add 和 Search 为什么有不同失败策略？

Add 正在建立新的可检索记忆：启用的模型失败，就不应假装已经完成分析与索引。因此图片分析或文本 embedding 失败时不提交数据库，返回 503。Search 正在读取已有资料：某条模型路线失败，还可能用词法或哈希找到证据，所以允许降级。

场景当前行为注意
Add 视觉输出非法／超时503，不提交记忆已发生的远程费用不会因此自动退款
Add embedding 失败503，不提交记忆重试前的图片分析若未提交缓存，可能重新调用
Search 视觉失败已有文字／哈希继续不保证没有文字的新图片能被搜到
Search embedding 失败BM25／图片哈希继续语义路线缺失，召回可能下降
返回证据时原图丢失503，而非静默返回坏图片相同 Add 重试可补图
数据库写事务失败消息、向量、缓存、请求状态回滚可能留下已保存但未引用的原图文件

幂等和缓存解决的是两个问题

幂等回答“同一次请求重试会不会多写一条？”键是 user_id + request_id，并核对 payload_hash。缓存回答“这张图片在同版本模型下是不是已经分析过？”键是 user_id + media_key + analysis version。

同一用户换一个请求 ID 上传相同图：会新增一条消息，但可以复用分析缓存。原请求原样重试：不会新增消息。另一用户上传相同图：不复用前一用户的分析缓存；每个用户也有自己的媒体 key 范围。

并发并不等于“所有计算只发生一次”

两个请求可能同时发现没有缓存，然后各自调用模型。数据库在提交时防止重复记录，但当前没有跨进程 single-flight，因此无法保证只产生一次远程调用费用。不要把“数据库不重复写”理解成“模型一定不重复算”。

用户隔离做到哪一层？

Units、向量查找、幂等记录、缓存均包含用户范围；图片路径也以用户哈希分目录。但 API Key 是整个服务级的，不会证明调用者真的拥有传入的 user_id。当前假设调用服务的一方可信，适合本地 demo，不是多租户生产鉴权系统。

容量与隐私边界

单图最多 10 MiB，Add 图片合计最多 30 MiB，Search 返回图片累计预算 30 MiB。媒体恢复超预算时跳过候选，可能少于 top_k。还没有整体 HTTP 请求体上限、速率限制、自动删除或 TTL。默认只监听本机；不要直接开放成公网服务。

视觉开关开启会上传图片到配置的服务。分析报告虽然不包含 Base64，也可能包含图片中的个人信息。提示词要求忽略图中指令不等于完全防御提示注入；派生文字必须继续当作不可信数据。

怎么检查一张真实图片？

先配置好至少一种分析器。独立 OCR 需另行安装 Tesseract 与语言包；远程服务需确认图片输入支持。再运行：

.\.conda\python.exe scripts\inspect_image.py --image .\你的图片.png --query '型号 M42'
# 已开启远程视觉时，额外添加 --allow-remote，明确允许上传与可能的费用

脚本建立临时数据库，只上传原图，不把你的查询提前写进消息。报告保存在 data/evaluations/images。先读 image_artifacts 看描述与 OCR 是否真实，再看检索。只有一张候选时，向量也可能把无关问题返回为第一名，所以这不是准确率评测。

旧图怎样补分析？

# 只读预览：不迁移数据库，不调用模型
.\.conda\python.exe scripts\backfill_images.py --user-id alice

# 停止 API 写入，备份数据库和媒体，并配置分析器后再应用
.\.conda\python.exe scripts\backfill_images.py --user-id alice --apply
# 远程视觉同样需要额外 --allow-remote

工具按消息提交，重建派生记录和派生向量，保留原文与原文向量。中途失败，前面完成的消息仍保留，可重试。它不是更换 embedding 后的全量原文索引重建工具。旧数据库启动时的 source 迁移，也只是改变结构，不会替旧图片调用模型。

升级前为什么建议备份？

V0.1 的向量主键没有 source，V0.2 迁移后旧向量作为 text 保留。虽然有兼容测试，但旧版写入代码未必兼容新结构，所以“把代码退回去”不等于完整回滚数据。正式数据升级前，应停止写入并保留数据库与媒体副本。

网页三列应该怎样看？

同一个问题，左列 BM25、中列 Dense、右列 RRF，分别展示找到的历史消息，不是三份新生成的答案。卡片 #1 · D1:5 · assistant 表示：本路线第 1 名，来自第 1 次会话的第 5 轮，是当时助手的消息。user 与 assistant 是两条不同消息，可以同时占据两个结果位置。

绿色“命中标注轮次”表示消息所在 round 出现在该问题的 clue 参考名单里。另一条同轮消息也可能算命中，因为目前计分是轮次级，而不是逐条内容是否足够回答。灰色“非标注轮次”只表示不在名单中，不能直接断定无关。

用一个例子读懂四个数字

假设某题有三处参考轮次 A、B、C，前五条消息返回顺序是 X、A、A、B、Y。A 的两条消息按召回证据只算一个轮次。

指标这道题的值解释
Hit@51至少找回一处参考轮次
Recall@52/3三处中找到 A、B；不因重复 A 多算
MRR@51/2第一处参考证据排第 2
全部找回0C 没找回，不能算全部找到

上面的指标表，是用四个角度检查同一份结果：Hit 问“有没有找到一处”，Recall 问“应该找到的找齐了多少”，MRR 问“第一处找到得够不够靠前”，全部找回问“是不是一处都没漏”。它们不是四个不同的搜索算法。

总体表对有标注题求平均；无 clue 题只展示、不计分。Recall 100% 不代表五条消息都相关，只意味着参考轮次已经找齐。MRR 是小数评分，不是答案正确率或模型置信度。

公开数据诊断的限制

当前把场景全部历史入库，再测试选择的问题，不模拟提问时的历史截止。limit 是按原始顺序取前 N 题，不是随机代表样本。问题、答案与 clue 不写入记忆。--include-captions 只是把数据集已有描述加入文字，不调用我们的视觉模型，也不能当作视觉能力的实测。

查看一个失败问题的推荐顺序

读问题 → 读标注原文 → 读三路实际返回文本 → 看首次命中与召回率 → 再判断漏在提取、检索还是融合。没有读原文之前，不急着只根据红绿标签改算法。

为什么不保证“换什么都只改一个文件”？

合理架构减少无关耦合，但新能力仍会跨越几个模块。比如新增图片分析，需要任务模块、来源存储、Add 流程和装配一起配合。重点是各自只承担自己的部分，不是为了追求一个文件修改而把所有工作堆进同一个地方。

一个容易上手的小迭代

先拿几张铭牌图，用 inspect_image 看 visible_text 是否准确。如果目标型号没有提取出来，先调整 OCR / 视觉任务，而不是立刻修改 RRF。如果目标文字已经准确提取，却 BM25 没命中，再检查分词、用户范围和旧图是否完成补处理。

每次修改建议留下什么？

  1. 具体失败样例和原始结果。
  2. 一个明确假设，例如“型号中的连字符被分词拆开影响匹配”。
  3. 一次只改变少量因素的修复。
  4. 自动回归、真实样例对照和仍未解决的问题。
“我现在找不到可改进的地方”很正常。先有能观察问题的样例，再形成改动，不必为了迭代而更换看起来高级的算法。

把三种状态分开，
设计才不会变成误解。

已实现 当前代码链路

  • 真实图片集合中的召回、误检、模型幻觉、延迟和费用。
  • 竞赛最新模型限制、资格、正式接口与官方 Smoke/Full。
  • 在更大数据量、长历史、多用户情境中的容量与性能。

未实现的东西

直接图片向量、真正的视觉相似图片查找、HNSW 等近似索引、LLM 最终回答、reranker、知识图谱、时间截止检索、自动拒答、完整原文 embedding 重建工具、按用户删除与 TTL、生产级多租户授权、Docker 与公网部署。

当前实现中值得记住的局限

向量按消息取最大片段相似度；API 不返回命中片段出处。BM25 对整条扩展文本打分。组合视觉和 OCR 不做结果冲突校验。缓存不保证并发模型调用只发生一次。文件和数据库之间没有原子跨系统提交。相关性阈值尚未建立，单候选返回不能证明有证据。

16 / Glossary

遇到一个名字，
先问它在这里指什么。

payload · 请求携带的数据
不是一种神秘格式。Add 中通常是包含 user_id、messages 等字段的字典；另一个函数里同名变量也可能指数据库里的一段 JSON，含义取决于上下文。
raw / bytes / Base64
raw 是原始图片字节。Base64 把二进制转成方便放进 JSON 的字符串，不是图片压缩或加密。parser 解码后才把 bytes 交给媒体保存与分析。
MIME
例如 image/png，说明媒体格式。不能只相信请求自报格式；我们会用实际字节核对。
key / media_key
图片在媒体目录里的相对标识。当前由用户哈希和图片字节哈希组成，不是密钥，也不是 embedding。
root / Path
root 是存储根目录。Python Path 的斜杠运算可拼路径：root / key 得到完整文件位置，不是在做数学除法。
Unit
记忆基本单元，当前是一条消息。它与“对话轮次”“图片”“向量片段”不是一回事。
artifact · 派生记录
图片分析产生的附加资料，包含描述、可见文字和来源版本。它不是用户原话，不能替代原始证据。
source / chunk_order
source 说明向量来自原文还是某张图的哪类派生文字；chunk_order 是这个来源内部的分片序号。
embedding / vector / index
embedding 是生成数值表示的过程或模型；vector 是结果；index 是帮助查找的组织结构。当前向量存 SQLite 并线性比较，没有复杂向量索引。
adapter · 适配器
把某个外部工具的具体调用方式，包装成项目需要的能力。比如 OllamaEmbedder 把 Ollama HTTP 接口包装成 embed()。
dependency injection · 依赖注入
需要工具的对象不在内部写死工具，而由外部通过参数传入。这与 SQL 注入或提示词注入不是同一种“注入”。
Protocol
描述对象要有哪些方法和属性的能力约定。它不等于必须继承的基类，也不自动验证网络响应。
pass / ...
pass 是 Python 的空操作占位，执行时什么都不做。三个点 ... 是 Ellipsis，也常用作接口方法体占位。看到它们不能推断功能已实现；要看这是接口声明、空壳，还是别处提供了真实对象。
transaction · 事务
把多次数据库修改作为一组提交或回滚。这里原始消息、向量、缓存和幂等记录同事务；磁盘图片不属于这一个 SQLite 事务。
idempotency · 幂等
同一个成功请求原样重试，不多写一份逻辑记忆。不是保证所有模型调用只执行一次。
cache / revision / provenance
cache 复用已有计算；revision 人工区分可变模型或语言包版本；provenance 记录“结果由谁、按什么配置生成”。
recall / retrieval / reranking
retrieval 是找回候选的过程；recall 是参考证据找回比例；reranking 是对候选再次精排。RRF 是排名融合，当前没有专门的重排模型。
local HTTP / 127.0.0.1
本机服务地址，其他电脑不能通过自己的 127.0.0.1 访问你的电脑。它不等于公网 IP；读离线文档不需要云服务器。

不必一次全懂，
先亲手追完一条路径。

理解项目不是背下每个文件。能解释一份输入怎样变成结果，知道出现问题时先看哪里，就已经是在建立工程能力。

第一轮：只追踪文字 Add

  1. 读 routes.py 的 add：body 怎样变成字典？
  2. 读 service.py 的 add：工具怎样传给 add_memory？
  3. 读 add.py：纯文字情况下哪些步骤会跳过？
  4. 读 parser.py：纯字符串返回哪四个值？
  5. 读 indexing.py：一条消息如何变成一组向量记录？
  6. 读 commit_add：数据库在哪里开始真正写入？

第二轮：在同一条消息里放一张图

先保持图片分析关闭，观察 media_key 与原图文件；再配置分析器，观察 image_artifacts。不要同时改分片、模型与排序。你要能解释：新增描述为什么没有出现在返回的用户原话里，却能参与搜索。

第三轮：追踪 Search

先看 query 的文字在哪里形成，再看三路候选的条件，然后看 RRF 与 compose。尝试解释“top_k=5，却返回少于 5 条”可能有哪些原因：候选本来少、去重、没有匹配，或者图片预算。

五个自查问题

1 · 为什么换 embedding 不应该重写 HTTP 路由？

路由只负责请求格式和调用 service。模型调用被适配器封装，具体对象在启动时装配。更换模型主要影响适配器、配置、版本和索引重建，而不是请求处理逻辑。

2 · 同一张图上传两次，为什么既可能新增消息，又可能不新增？

同一个成功 request_id 原样重试不新增；换 request_id 是新的 Add，可新增消息。图片文件与分析结果可能复用，这和消息是否新增是两个层级。

3 · OCR 已经写出了 M42，但查询仍然失败，先看什么？

先确认 OCR 派生记录真的提交到目标用户、目标数据库，旧图片是否补处理；再看查询词法和向量单路结果，最后看融合与输出预算。不要只凭模型日志“识别过”就认定可查询数据已经存在。

4 · 为什么一张图的检查成功，不能说明图片检索做好了？

没有干扰候选，也没有足够的无证据问题；向量即使对无关问题也可能返回唯一候选。需要多图集合、明确参考与人工核对提取内容。

5 · 关闭图片分析以后，已有描述就消失了吗？

不会。开关主要决定新 Add 和图片 query 是否调用分析器；已保存的 artifacts 仍参与 BM25，已有匹配版本向量仍可被查找。关闭调用不是删除已生成数据。

下一步建议做什么？

先确定一个真实视觉服务或本地 OCR 路径，拿几张有权使用的图片做提取检查。记录描述遗漏、型号误读、相似图片干扰，再决定要调整哪个模块。比赛规则和真实模型效果尚未验证的部分，继续作为独立任务推进。
